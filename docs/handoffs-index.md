Five documents, one shared shape: an agent who understands what "correct" or "healthy" means for a signal, a test, or a recovery scenario defines the specifics; Operations/SRE Engineer owns turning it into something that actually runs (an alert rule, a dashboard panel, a collector, a drill runbook). None of these describe work that's done — each is explicit about exactly how much of it is real today versus proposed, and none of them invent numbers or results that don't exist yet.

## What's shared across all five

- **The routing decision is made once, not per-handoff.** `reconciliation-alerting-handoff.md` §5 raises Alertmanager vs. Grafana's built-in unified alerting as an open question for SRE; every other handoff that needs alert routing (`observability-alerting-handoff.md`) explicitly reuses that decision rather than re-litigating it. `load-testing-handoff.md` and `recovery-drill-handoff.md` don't touch alerting at all — this one applies to the two that do, not to all five uniformly.
- **New infrastructure still needs an ADR.** `otel-tracing-handoff.md` §6 is explicit that a tracing backend (Tempo or otherwise) requires the same "What Not to Build" check Architect's `claude.md` entry already requires for any new infrastructure — the discipline that was missed once already on this project (the Helm/Kubernetes scope-creep finding, `docs/retrospectives/LESSONS.md`).
- **Reconciliation shows up as a dependency of two other handoffs, not just its own.** `recovery-drill-handoff.md` §3 names a post-restore reconciliation pass as the strongest available evidence a restore actually preserved correct data — one more reason the reconciliation job itself (still unbuilt) is worth prioritizing; it isn't only the observability/alerting concern its own handoff scopes it as.
- **None of these are load-bearing until SRE acts on them.** Each has its own `Acceptance criteria` checklist at the end — none are checked off yet. A handoff document existing is not the same as the thing it describes existing; treat these the same way `IMPLEMENTATION_PLAN.md`'s checkbox policy treats everything else in this repo — `[x]` only for what's verifiably delivered.

All five close out open items from `IMPLEMENTATION_PLAN.md` Phase 6/7/8/9 (SLI/SLO Definition, Alerting Strategy, Distributed Tracing, Load Testing, Source Reconciliation, Recovery Plan / Executed DR Drills) — see each phase for the authoritative checkbox status; this index is a map of the handoffs, not a duplicate tracker. `claude.md` is where each contributing agent's ownership and Key Focus is defined; this index exists because five separate cross-references from there would be harder to keep straight than one list.
